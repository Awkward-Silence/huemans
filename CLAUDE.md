# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

**huemans** is a mobile-first web app that breaks the ice at events: attendees answer a few funny questions, are split into **diverse color groups**, and share **one icebreaker for the night**. It is being built by a team of 4 (Adrián architect, Diego backend, Miguel fullstack, Daniel frontend) during a **24h hackathon**, for a 2-3 minute live demo to 10-15 people; the hackathon requires AI features. `api/` is scaffolded (skeleton only, no bounded context yet); `web/` and `contracts/` are not — add their commands below when they exist.

Sources of truth: `initial-raw-specs.md` (product spec, written by the team), `docs/next-steps.md` (plan, owners, open decisions), `docs/domain/` (DDD models), `docs/architecture/adr/` (architecture decisions), `openspec/changes/` (one change per backend lane).

## API commands (run inside `api/`)

```bash
pnpm install
cp .env.example .env && sed 's#/huemans$#/huemans_test#' .env.example > .env.test   # first time only
docker compose up -d                 # Postgres 17: databases huemans + huemans_test
pnpm migration:up && pnpm migration:up:test
pnpm seed:demo                       # demo event 0199c0de-0000-7000-8000-000000000001 (idempotent)
pnpm start:dev                       # http://localhost:3000/health
pnpm lint && pnpm build

pnpm test                            # all suites (Integration/Functional need Postgres up)
pnpm test:unit | test:integration | test:functional
pnpm jest tests/Unit/Shared/Domain/ValueObject/Uuid.test.ts   # one file
pnpm jest -t "testRejectsVersion4"                            # one test by name
pnpm migration:create                # new migration in api/migrations
```

- Layout: a single NestJS app — entry `src/main.ts`, `AppModule` in `src/app.module.ts`; each bounded context in `src/<BC>/{Domain,Application,Infrastructure}` (ports in `Domain/Port`, one `Application/ApplicationService.ts`, `Infrastructure/{Http,Persistence/MikroOrm,<BC>Module.ts}`); alias `@Huemans/*` -> `src/*`.
- Persistence is MikroORM `EntitySchema` + value-object column types (`VO.uuid/string/number/enum` in `src/Shared/Infrastructure/Persistence/MikroOrm/Types`); schema files must be named `*Schema.ts` to be discovered. Never put ORM or Nest decorators in `Domain/` — `pnpm lint` fails on it.
- Integration tests use `tests/Support/integration.ts` (`bootIntegration`, `clearDatabase`); functional tests use `tests/Support/functional.ts` (`bootFunctional`, `getJson`, `postJson`). The MikroORM CLI does not read `.env` by itself — always go through the `migration:*` scripts.

## Product flow (what the demo must do)

```
QR (web URL) -> 2-3s intro -> enter name -> 4-5 multiple-choice questions, soft 20-30s timer
  -> suspense CTA -> reveal: group color + personality type -> live color distribution
  -> host taps "reveal" -> the night's ONE icebreaker on every phone -> LED badge mode
```

- The timer is **soft**: late answers are accepted, never rejected.
- Join is anonymous (name only); the client keeps the attendee id so a reload resumes.
- Nice-to-have only: % match / per-person icebreaker, meeting spots, "people you already know".

## Domain rules that are easy to get wrong

- **Groups are built for diversity, not similarity.** A color is a group label, not a personality. Each attendee gets one of 4 **personality types** (majority of their answers' traits via the trait-type mapping), and is placed in the smallest group that has the fewest members of their type. The raw spec's "50% red / 50% blue" example predates this decision — follow `docs/domain/color-distribution/model.md`.
- Group sizes never differ by more than 1; assignments are final (no withdraw, no re-balancing); the icebreaker reveal does not stop late joiners from being assigned. Remaining ties go amber, coral, teal, violet.
- The host's **reveal** moves the event `open` -> `revealed` (once; a second tap is a no-op) and Event emits `EventRevealed`. Night Icebreaker reacts by picking the night's icebreaker from the room's aggregated traits and storing it in **its own aggregate**, not on the event (`docs/domain/event/model.md`).
- Quiz settings (5 questions, 20 s soft timer) are fixed for the MVP and belong to Participation's quiz, not to Event.
- Shared kernel (`docs/domain/shared-kernel/model.md`): `Trait` (33 values), `EventId` and `AttendeeId` (UUIDv7, generated by the issuing context).
- Closed value sets live in their owner's value objects: `Trait`, `PersonalityType` and `Color` in `api/src/Shared/Domain/ValueObject/` (shared kernel), `Theme` in `api/src/Catalog/Domain/ValueObject/`. The catalog JSON schemas live in `api/src/Catalog/Infrastructure/Content/` (see `docs/domain/catalog/model.md`). `tools/` validates its JSON against them (`npm run validate` / `validate:icebreakers`, which need `api/` installed for `zod`). The files `tools/` imports use relative imports, not `@Huemans/*`. Catalog content (50 questions, 51 icebreakers) stays in `tools/` as JSON; `api/` must never import `tools/`.

## Architecture

All TypeScript. Each app has **its own `package.json` and `node_modules`** — no workspaces, no shared dependencies.

```
contracts/   types only: no package.json, no runtime imports
web/         React (Vite), mobile first: /join/:eventId (attendee), /host/:eventId (big screen)
api/         NestJS + Mastra (in-process), Postgres, one Nest module per bounded context
tools/       content and validation scripts (not production code)
```

- **Contracts:** apps consume `contracts/` only via `import type ... from '../contracts/...'`, so it is erased at compile time. Never add a runtime import or dependency to it.
- **Bounded contexts in `api/`:** catalog, event, participation, color distribution (core domain, full DDD + tests), room (read-only: the live room read across Event, Color Distribution and Participation), night icebreaker, agents. Each keeps a `domain/` folder free of NestJS decorators.
- **Domain events belong to the context that publishes them** (Event owns `EventCreated`/`EventRevealed`, Participation owns `QuestionnaireCompleted`); other contexts subscribe. Handlers are synchronous and in-process: no queue or background job.
- **Key seam:** Participation publishes `QuestionnaireCompleted` with the attendee's trait profile; Color Distribution emits `AttendeeGrouped { eventId, attendeeId, color, personalityType }`, pushed in realtime to the phone and host screen.
- **Agents enrich, they never decide or block.** Mastra runs inside NestJS behind ports (`ColorExplainer`, `IcebreakerExplainer`), each with a static fallback. No LLM call in the join, answer, distribution or close paths.

## Architecture decisions

New code follows the ADRs in `docs/architecture/adr/` ([index](docs/architecture/adr/README.md)). A change that deviates from one needs a new ADR that supersedes it.

- [ADR-001](docs/architecture/adr/ADR-001-tdd-outside-in.md) TDD outside-in: functional tests for acceptance criteria, unit tests for the domain, integration tests against real Postgres; no unit tests for application services or DTOs; camelCase `testXxx` names.
- [ADR-002](docs/architecture/adr/ADR-002-tell-dont-ask.md) Tell, Don't Ask: business logic in intention-named domain methods; application services only orchestrate.
- [ADR-003](docs/architecture/adr/ADR-003-value-objects.md) No primitives in the domain: immutable value objects that validate themselves; composite concepts are one VO.
- [ADR-004](docs/architecture/adr/ADR-004-aggregate-identity-and-domain-events.md) Aggregates generate their own UUIDv7 id and record events; events are dispatched only after a successful save.
- [ADR-005](docs/architecture/adr/ADR-005-references-by-id.md) Aggregates reference each other (and other contexts) by typed id only.
- [ADR-006](docs/architecture/adr/ADR-006-canonical-dtos.md) One `toDTO()` per aggregate; no domain object crosses the boundary.
- [ADR-007](docs/architecture/adr/ADR-007-domain-free-of-infrastructure.md) `Domain/` imports no Nest, ORM or HTTP; mapping lives in `*Schema.ts` (enforced by `pnpm lint`).
- [ADR-008](docs/architecture/adr/ADR-008-application-service-no-buses.md) One `ApplicationService` per context, one method per use case; no command or query bus.
- [ADR-009](docs/architecture/adr/ADR-009-criteria-for-dynamic-queries.md) Named repository methods for frequent queries; a `Criteria` object only for dynamic ones.
- [ADR-010](docs/architecture/adr/ADR-010-explicit-optionality.md) Optional domain data is explicit inside the domain and plain at the boundary.
- [ADR-011](docs/architecture/adr/ADR-011-typed-validation-at-the-edge.md) Every external input is validated by a typed payload (zod pipe) before reaching the application service.
