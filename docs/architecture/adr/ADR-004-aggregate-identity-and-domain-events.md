# ADR-004: Aggregate identity and domain events

**Status:** Accepted (2026-10-10)

## Context

Ids generated by the database make an aggregate incomplete until it is saved. Events dispatched from inside an aggregate fire before the change is persisted, so subscribers can react to something that never happened.

## Decision

- The aggregate generates its own id in the domain layer, never through database autoincrement. Ids are time-ordered (UUIDv7), not random UUIDv4.
- The aggregate records domain events when its state changes and exposes them (`pullDomainEvents()`). It never dispatches them itself.
- The orchestrator dispatches the pulled events **only after the save succeeded**. A failed save publishes nothing.

## Consequences

Aggregates are complete from construction, and ids sort by creation time. A subscriber failure after the save does not roll the save back (accepted: the save is what realistically fails).

## In this repo

- `AggregateRoot` (`api/src/Shared/Domain/AggregateRoot.ts`): `record` and `pullDomainEvents`.
- `EventId`/`AttendeeId` extend `Uuid`, which only accepts UUIDv7.
- `Event/Application/ApplicationService.create`: save, then `dispatchAll(event.pullDomainEvents())`.
- **Known deviation:** `Event.create` receives `EventId.random()` from the application service instead of generating it itself.
- **Known deviation:** `Event/Application/ApplicationService.reveal` saves and dispatches `EventRevealed` inside one transaction, with the event row locked. Night Icebreaker's pick joins that transaction, so a failed pick rolls the reveal back and the host can tap again; otherwise the event would stay revealed with no icebreaker and no way to retry (`openspec/changes/night-icebreaker/design.md`).
